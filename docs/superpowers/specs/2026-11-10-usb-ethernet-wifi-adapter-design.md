# USB‑Ethernet → Wi‑Fi адаптер для Blackmagic Micro Studio Camera 4K G2

## Контекст і навіщо

Камера Blackmagic Micro Studio Camera 4K G2 віддає REST API (Camera Control REST API) лише через
USB‑C Ethernet адаптер. Якщо підключити її кабелем до телефону з тетерингом, нічого не працює:
камера розуміє тільки «USB‑мережеву карту». Хочеться керувати камерою з телефону через власний
застосунок, який сам знаходить камеру через mDNS або за IP, введеним вручну.

Рішення: прошивка для ESP32‑S3 (поки Cardputer ADV, згодом гола плата ESP32‑S3 з однією кнопкою).
Пристрій вставляється в USB‑C камери і від неї ж живиться. Для камери він виглядає як USB‑Ethernet
адаптер, а назовні роздає власну Wi‑Fi мережу. Телефон підключається до неї і бачить камеру так,
ніби вони обидва в одному світчі.

**Успіх:** вставив адаптер у камеру, телефон підключився до Wi‑Fi «BMCam‑XXXX», застосунок сам
знайшов камеру через mDNS і керує нею. Жодних налаштувань на телефоні чи камері, крім DHCP на камері.

## Цілі / не‑цілі / анти‑цілі

**Цілі (з розмови):**
- Одна камера ↔ один телефон; адаптер працює як Wi‑Fi точка доступу (AP).
- Прозорий L2‑міст: mDNS/broadcast проходять в обидва боки, камера доступна за власною IP.
- Налаштування (назва мережі, пароль) через веб‑сторінку на самому адаптері.
- Скидання налаштувань до заводських кнопкою.
- Живлення від камери по USB.

**Не‑цілі:** кілька камер; режим клієнта (підключення до чужої Wi‑Fi чи хотспоту телефону);
доступ камери чи телефону в інтернет через адаптер; власний UI для керування камерою; відео через Wi‑Fi.

**Анти‑цілі:** адаптер, що вимагає ручного налаштування IP на телефоні; рішення, яке ламає mDNS‑пошук;
телефон, який утрачає мобільний інтернет через те, що адаптер «прикидається» шлюзом.

## Головний ризик → спайк першим

Офіційного списку сумісних адаптерів немає (Blackmagic радить Belkin, Cyanview пише, що працює
«більшість»). ESP32‑S3 просто стає **класовим** USB‑мережевим пристроєм (NCM / ECM / RNDIS).
Прикинутися конкретним чипом (ASIX/Realtek) теоретично можна через vendor‑клас TinyUSB, але це дорого.
Якщо в камері немає драйвера класу, базовий задум не спрацює. Тому крок 0 — це одноразовий спайк,
щоб відповісти «так» чи «ні» до будь‑якої іншої роботи.

Другий ризик: чи відповідає камера на mDNS на USB‑Ethernet інтерфейсі. Застосунок CamCtrl
(`~/work/my-apps/camctrl/camctrl-flutter`) шукає камеру так: робить `InternetAddress.lookup` відомих
імен хостів (`micro-studio-camera-4k-g2.local` тощо, `lib/utils/constants.dart`
`DiscoveryConstants.knownCameraHostnames`), а потім перевіряє HTTP‑заголовок `Server: BlackmagicDesign`
(`lib/services/camera_discovery_service.dart`). Значить, потрібна саме відповідь на mDNS A‑запит
про ім'я хоста, перегляд сервісів не потрібен. Прозорий міст передає відповідь камери як є.
Перевіряємо на кроці 1. **Запасний варіант:** якщо камера не відповідає, адаптер сам відповідає
на A‑запит `micro-studio-camera-4k-g2.local` → IP камери. Ім'я змінюється на веб‑сторінці.
Відповідає лише тоді, коли камера мовчить, щоб не було конфлікту імен.
HTTP і WebSocket (`/control/api/v1/event/websocket`) ідуть напряму через міст, без проксі.

**Телефони: iOS і Android.** Прошивка тут нічого не змінює, але в README треба пояснити:
на iOS застосунку потрібен дозвіл Local Network; на Android мережа без інтернету «невалідна»,
тож застосунок має прив'язатися до Wi‑Fi (`bindProcessToNetwork`), інакше запити підуть через
мобільні дані. Можливо, буде окрема задача для CamCtrl (поза цим проєктом).

**Якщо камера не прийме жоден стандартний клас:** зупиняємось і повертаємось до обговорення
(рішення користувача). Емуляцію чипа ASIX/Realtek не робимо.

## Рішення щодо «як» (мої, не погоджені з користувачем, видно в плані)

- **ESP‑IDF 5.x замість Arduino 2.0.17.** Готові бібліотеки Arduino 2.0.17 не містять мережевого
  класу TinyUSB (NCM/ECM). Потрібні `espressif/esp_tinyusb` (NET: NCM, ECM/RNDIS) і низькорівневий
  доступ до кадрів Wi‑Fi AP. Збірка: PlatformIO `framework = espidf` (як звик користувач),
  а якщо керовані компоненти там не зберуться, то чистий `idf.py`. Остаточно вирішує виконавець.
- **Дисплей:** M5GFX як компонент ESP‑IDF (він це підтримує). M5Unified/M5Cardputer не потрібні:
  з периферії потрібні лише екран і кнопка G0.
- **Міст L2 з трьома «портами»:** USB NCM ↔ Wi‑Fi AP ↔ власний lwIP netif адаптера.
  Два варіанти (вибір за виконавцем, вимога однакова):
  (a) lwIP bridgeif через `esp_netif_br_glue` (приклад `examples/network/bridge`), де NCM загорнутий
  у netif з власним драйвером;
  (b) власний простий форвардер: `esp_wifi_internal_reg_rxcb(WIFI_IF_AP)` / `esp_wifi_internal_tx`
  ↔ `tud_network_recv_cb` / `tud_network_xmit` плюс таблиця MAC, а кадри для MAC адаптера
  йдуть у lwIP. Broadcast і multicast розсилаються на всі порти.
  Логіку рішення «куди відправити кадр» робимо чистою функцією і покриваємо native‑тестами.
- **IP‑план:** адаптер `192.168.73.1/24`, DHCP‑сервер на netif адаптера обслуговує обидва боки.
  Клієнт з боку USB (камера) завжди отримує `192.168.73.2`, щоб для ручного введення IP була
  передбачувана адреса. Wi‑Fi клієнти отримують `.10–.50`.
  Вбудований `dhcpserver` ESP‑IDF не вміє резервувати адресу за MAC. Тому пишемо власний
  маленький DHCP‑сервер (DISCOVER/OFFER/REQUEST/ACK, без опцій router і DNS). Його розбір і формування
  пакетів — чиста логіка з native‑тестами. Камеру впізнаємо за тим, що кадр прийшов з боку USB.
  **DHCP не віддає шлюз і DNS:** телефон лишає мобільний інтернет і ходить у Wi‑Fi лише по локальній
  підмережі. Камера має стояти на DHCP (це піде в README).
- **USB:** спершу NCM. Запасний варіант — комбінований режим esp_tinyusb `TINYUSB_NET_MODE_ECM_RNDIS`
  (одна прошивка з двома USB‑конфігураціями, вибір в Kconfig).
  Опційно composite із CDC‑ACM для логів (вимикач на випадок, якщо камера не сприйме composite).
- **Wi‑Fi за замовчуванням:** SSID `BMCam-XXXX` (останні 2 байти MAC), пароль фіксований
  `blackmagic`. Його видно на екрані Cardputer і в README; на платі без екрана його треба просто знати.
  Канал 6, WPA2‑PSK. Налаштування зберігаються в NVS.
- **Веб‑сторінка** на `http://192.168.73.1/`:
  - статус: чи підключена камера по USB, IP камери (посилання), кількість Wi‑Fi клієнтів;
  - форма: SSID (1–32 символи), пароль (8–63 символи), канал (1–13). Зберегти → перезавантаження.
  Окремої авторизації немає, захищає пароль Wi‑Fi.
- **Кнопка:** утримання ≥ 5 с → скидання до заводських (стирання налаштувань у NVS) і перезавантаження.
  Cardputer: G0 (GPIO0). Для майбутньої плати пін задається в Kconfig.
- **Екран Cardputer:** SSID, пароль, IP адаптера, стан USB (камера є/немає), IP камери, кількість
  клієнтів, підказка про скидання. Клавіатура не використовується.
- **Шар плати:** `board_cardputer` (екран + G0 + RGB‑LED на GPIO38 з урахуванням нюансу з підсвіткою)
  і `board_generic` (кнопка + опційний LED). Ядро від плати не залежить.

## Етапи

0. **Спайк (одноразовий):** NCM‑пристрій + DHCP‑сервер на `192.168.73.1`, на екрані видані адреси
   і стан USB. Перевірка на Linux‑ПК (`cdc_ncm` → інтерфейс `usbX`, отримав IP, ping), потім
   **користувач** вставляє Cardputer у камеру: чи видала адаптер камері адресу і чи відповідає
   `curl http://192.168.73.2/control/api/v1/...` (з ПК через USB не вийде, тому це перевіримо на кроці 1).
   Якщо NCM не працює, пробуємо ECM, потім RNDIS. Якщо не працює жоден, зупиняємось і переобговорюємо.
1. **Міст USB ↔ Wi‑Fi AP + netif адаптера**, DHCP з резервуванням `.2`, проходження mDNS.
   Перевірка на камері: чи резолвиться `micro-studio-camera-4k-g2.local` з телефону/ноутбука.
   Якщо ні, вмикаємо запасний mDNS‑респондер.
2. **Налаштування:** NVS‑сховище, веб‑сторінка, валідація, скидання кнопкою.
3. **Екран і шар плати** (Cardputer + generic).
4. **README:** перепрошивка (USB зайнятий мережею, тому для режиму завантаження треба вимкнути живлення
   Cardputer перемикачем або натиснути reset, затиснути G0 і тоді підключити USB; саме підключення
   USB не перезавантажує плату, бо вона живиться від батареї), налаштування камери (DHCP),
   заводські налаштування.

## Структура проєкту (орієнтовно)

the repository root:
- `main/` — `app_main`, `usb_net.*` (TinyUSB NCM), `wifi_ap.*`, `bridge.*` (форвардер/br_glue),
  `dhcp.*` (сервер + резервування), `web.*` (esp_http_server + вбудований HTML), `settings.*` (NVS),
  `button.*`, `display.*` (лише Cardputer).
- `main/logic/` — без залежностей від IDF: рішення про форвардинг кадрів / MAC‑таблиця, валідація
  налаштувань, генерація SSID, розбір форми. Native‑тести (Unity), як у прикладі
  (the Molfar for Cardputer ADV project, `test/` + `pio test -e native`).
- `boards/` або Kconfig‑вибір плати.
- Що взяти з прикладу: підхід до SSID з MAC (`src/hw/SoftAp.cpp`, `logic/ApCredentials`),
  розділення logic/hw з native‑тестами, нюанс GPIO38 (`hw/StatusLed`).

## Перевірка

- **Unit:** `pio test -e native` для `main/logic/*` (форвардинг, валідація, SSID, розбір форми).
- **Стенд на одному Linux‑ПК (ПК замість камери):** Cardputer по USB → інтерфейс `usbX`.
  Переносимо його в netns `cam` (`sudo ip netns ...`). Всередині запускаємо DHCP‑клієнт і мок REST
  (python, відповідає з `Server: BlackmagicDesign` на `/control/api/v1/system/product`) та публікуємо
  ім'я хоста `micro-studio-camera-4k-g2.local` (`avahi-publish -a`). Потім ще раз без публікації,
  щоб перевірити запасний респондер.
  Wi‑Fi ПК (AX211) підключається до `BMCam-XXXX`.
  Очікування: ПК отримав адресу з `.10–.50` без шлюзу; `curl http://192.168.73.2/...` працює;
  `avahi-resolve -n micro-studio-camera-4k-g2.local` → `192.168.73.2`; веб‑сторінка `192.168.73.1` показує статус і зберігає налаштування.
  Для netns потрібен sudo, тож ці команди запускає користувач.
- **На камері (користувач):** вставити адаптер, підключити телефон, застосунок знаходить камеру через mDNS;
  також перевірити ручне введення `192.168.73.2`. Утримання G0 5 с → заводські налаштування.
- **Живлення:** адаптер стабільно живиться від камери (без розряду батареї Cardputer).

## Що лишається виконавцю

Варіант мосту (a/b), PlatformIO чи idf.py, верстка веб‑сторінки, розміри буферів і черг,
конкретна верстка екрана, чи вмикати CDC‑ACM за замовчуванням.
